# M4: auto-pause and alerts

A VM that nobody is using pauses itself (M3's pause: memory and disk saved to
ZFS, RAM handed back). When an agent finishes or needs you, your phone gets a
push notification through [ntfy](https://ntfy.sh). Typing into a paused VM's
terminal wakes it. M4's other half, sign-in with Clerk, is in the plan.

## Set it up

```sh
bun run secrets --ntfy     # creates a private topic and prints its name
bun run deploy:host        # hostd reads the topic when it starts
bun run images:build       # VMs need the new guest agent and agent hooks
```

Subscribe to the printed topic in the ntfy app ([Android](https://play.google.com/store/apps/details?id=io.heckel.ntfy),
[iOS](https://apps.apple.com/app/ntfy/id1625396347)) or at `https://ntfy.sh/<topic>`.
ntfy.sh topics are open to anyone who knows the name, so keep it private.
Alerts carry only the VM's name and what the agent wants, never its output.
Without a topic, alerts only go to hostd's log (`journalctl -u substrate-hostd`).

Only VMs created from an image built after this have the hooks and the newer
guest agent. Older VMs keep working but never pause themselves.

## What counts as idle

guestd tracks when the VM was last active. Any of these resets the clock:

- output in any terminal session, or someone typing in one or opening it
- an agent event (below)
- the CPUs averaging more than 0.2 of a CPU's worth of work over 10 s, so a
  build or test run with no output still counts

The guest's monotonic clock is used, so a guest clock change can't trigger a pause.

## Agent events

Each agent reports through `substrate-event AGENT start|stop|attention [JSON]`,
which posts to guestd on a Unix socket (`/run/substrate/events.sock`). The image
sets up each agent:

| Agent | Where | start | stop | attention |
|---|---|---|---|---|
| Claude Code | `~/.claude/settings.json` hooks | `UserPromptSubmit` | `Stop` | `Notification` (permission prompts and questions only, not `idle_prompt`) |
| Codex | `notify` in `~/.codex/config.toml` | | `agent-turn-complete` | |
| OpenCode | `~/.config/opencode/plugins/substrate.js` | | `session.idle` | `permission.asked` |
| Antigravity (`agy`) | no hooks yet; the idle check covers it | | | |

The hooks only add to each agent's settings; everything else in those files is
yours to change. You can also send events yourself, e.g.
`make test; substrate-event claude stop` to get an alert when a long run ends.

## Alerts and pausing

hostd asks each running VM's guestd for its activity every 5 s
(`GET /activity` on the token-protected port). The ntfy topic stays on the host,
so nothing inside a VM can read or forge alerts on its own. Then hostd:

- Sends an alert for each new `stop` (default priority) or `attention` (high
  priority: sound and a pop-up). It skips them while someone typed in that VM
  within the last 2 minutes, since they're watching, so a chat at the keyboard
  doesn't buzz your phone after every reply. Tapping an alert opens the VM.
- Pauses the VM once it has been idle for its auto-pause setting (10 minutes by
  default) and has been awake at least that long, then sends a quiet alert.
  The awake rule matters after a resume: the guest's idle clock may include
  the time it spent paused.

| Change it | How |
|---|---|
| Web UI | The **Auto-pause** menu under the VM's name: Off, or 5 min to 4 h |
| CLI | `bun run vm auto-pause demo 30`, or `off` |
| API | `PATCH /vms/:id` with `{"autoPauseMinutes": 30}` or `null` |

## Waking it

When a VM pauses, its open terminal stays on screen with its last output,
marked **Paused**. The first key you type wakes the VM, and the terminal
reconnects to the same session with its scrollback. That first key is not sent
on, because you can't see yet what it would be answering (it could be a
permission prompt). The **Resume** button does the same. Typing while a VM is
still saving wakes it as soon as the save finishes.

## Limits

- Pausing a 16 GB VM takes 7–42 s (M3). Diff snapshots, which would have made
  it 2–3 s, were dropped.
- The public URL gives up on a request after 60 s (CloudFront's read
  timeout), so waking a VM while a slow save is still running can report an
  error even though it completes; the list catches up within 5 s.
- Alerts go to one topic, the host owner's. Per-user topics come with Phase 2.
- A program that keeps redrawing the screen, like `htop`, keeps the VM awake.

## Verify on AWS

```sh
bun run vm create --name demo --size small
bun run vm auto-pause demo 1
bun run vm exec demo -- 'echo "{\"notification_type\":\"permission_prompt\",\"message\":\"test\"}" | substrate-event claude attention'
curl -s "https://ntfy.sh/<topic>/json?poll=1&since=5m"   # the alert
bun run vm list                                           # paused a minute later
```

### AWS results, 2026-10-23

On a small VM (2 vCPU / 4 GiB) from image `20261023-165359`:

- Each agent's hook, run the way the agent runs it, reached ntfy within the
  5 s poll: Claude Code `Stop` and a permission `Notification`, Codex
  `agent-turn-complete`, and OpenCode `session.idle` through the plugin itself.
  Claude's `idle_prompt` was dropped, and no agent output was sent.
- With auto-pause at 1 minute, the VM paused 63 s after its last activity and
  sent the quiet "paused" alert. Resume took 265 ms. A background process (same
  PID) and the terminal session survived.
- After resuming, it stayed up for a full idle minute before pausing again,
  rather than pausing straight away.
- In a headless browser through the local UI: with a terminal open and idle,
  the VM paused, and the terminal kept its output and showed **Paused**. One
  key woke it within a second, the scrollback was intact, and the key itself
  wasn't sent to the shell.
- Typechecking, 73 local tests (one Linux-only test skipped on macOS) and the
  web build pass.

Not tested with a signed-in agent doing real work, since that needs an
account inside the VM; the hooks were run exactly as each agent runs them.
