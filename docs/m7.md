# M7: hardening for 24-hour runs

Agents can now run unattended for a day without a crash, a full disk, or a
stuck loop costing you their work. Diff snapshots, also planned for M7, were
dropped: pauses stay full saves (7–42 s for a 16 GB VM).

## A maximum run time

Each VM pauses itself once it has been awake for its limit, 24 hours by default,
even while busy, and sends an alert. Waking it starts the clock again. Auto-pause
(M4) still pauses an idle VM much sooner.

| Change it | How |
|---|---|
| Web UI | The **Max run** menu under the VM's name: No limit, or 4 h to 72 h |
| CLI | `bun run vm max-run demo 48`, or `off` |
| API | `PATCH /vms/:id` with `{"maxAwakeHours": 48}` or `null` |

## Crashes come back

hostd records which VMs should be running (`shouldRun` in each `vm.json`): set
when one is created, started or resumed, and cleared when you stop it. Every 5 s
the supervisor boots again any VM that should be running but isn't, and isn't
paused. That covers:

- a host crash or reboot, since hostd's first pass after starting brings them back
- a guest kernel panic or a VM process dying
- `sudo reboot` inside the VM, which used to stop it

A VM that goes down 3 times within 30 minutes is left stopped, with an alert;
starting it gives it another chance. Paused VMs stay paused through all of this.

### Sessions reopen

guestd keeps a list of its running sessions on the VM's disk
(`/var/lib/substrate-guestd/sessions.json`). When hostd brings a VM back, it tells
guestd so through the metadata service (`resumeSessions`). guestd then reopens
each session under the same ID, so an open browser tab reattaches. Agents pick
up their most recent conversation:

| Agent | Restarted as |
|---|---|
| Claude Code | `claude --continue` |
| Codex | `codex resume --last` |
| OpenCode | `opencode --continue` |
| Antigravity | `agy` (it has no such option) |

Shells come back as fresh shells. Scrollback and running processes are lost,
since the VM really did restart; the session starts with a line saying so. A
normal stop and start reopens nothing, as before.

## A save that can't be restored

If resuming a paused VM fails twice, for example because the saved memory came
from another Firecracker version, hostd stops refusing (M3's behaviour). It
rolls the disk back to the one saved with that memory, boots the VM fresh from
it, reopens its sessions as above, and sends a high-priority alert saying why.
The saved memory stays on disk until the VM's next pause or stop.

## Disks grow on request

```sh
bun run vm disk demo 64    # or POST /vms/:id/disk {"diskGib": 64}
```

Disks only grow, up to the size of the host's storage pool. A running VM gets the
space at once: hostd grows its ZFS volume and tells Firecracker, which tells the
guest. The guest then grows its filesystem with the ext4 resize ioctl, since
resize2fs can't open a mounted disk under Firecracker's kernel config. A stopped
VM is grown on the host. A paused VM must be resumed first, because its saved
state records the old size.

## Daily snapshots of the data disk

Data Lifecycle Manager snapshots the host's data disk every day at 21:30 UTC
(03:00 in India) and keeps 7. That disk holds every VM's disk and saved memory.
ZFS keeps its pool consistent on disk at every moment, so a snapshot of the live
disk restores like a power cut, losing at most a few seconds of writes. Turning
it on takes `bun run deploy:infra`.

Restoring is manual and not scripted yet. A snapshot becomes a new EBS volume in
ap-south-1a, which has to take the data disk's place while the host is stopped.
The stack attaches the data disk by its volume ID, and host setup waits for that
ID, so the swap needs a stack change too. Work that out when it's first needed.

## Health checks and logs

hostd's `/health` now includes the storage pool's state, size and how full it is.
Each image build also removes old images (1.5 GB each), keeping the newest two
and any that a VM's disk was cloned from; they had filled 30% of the pool.
hostd sends alerts when:

| What | When |
|---|---|
| Storage filling up | at 80% full, and again (high priority) at 90%; again after dropping below 75% |
| Storage unhealthy | the ZFS pool isn't `ONLINE` |
| A VM not answering | its guest agent hasn't answered for 2 minutes, e.g. out of memory |
| A VM restarted | after a crash, or from its save |

Logs come over SSM, so nothing needs to be open:

```sh
bun run logs host         # hostd: lifecycle, auto-pause, alerts, recoveries
bun run logs control      # the control API
bun run logs demo -n 50   # a VM's console, then its own journal if it's running
```

Failed requests are logged on one line now, rather than as a stack of minified
source.

### Leftover saves

A save (memory file plus disk snapshot) can be as big as the VM's RAM, so none
are left lying around. Stopping a VM deletes its save, even if the VM had already
crashed, and so does rolling it back to a run checkpoint. When hostd starts, it
also removes any save, pause snapshot or fork staging snapshot that a VM's record
doesn't name; a crash mid-pause or mid-fork can leave those behind. It never
removes the save a record names, since a VM resumed from it reads its memory file
for as long as it runs. Each removal is logged (`prune vm-…: removed …`), and one
that fails is logged and skipped, so it can't stop hostd from starting.

## Verify on AWS

### AWS results, 2026-10-23

On a small VM (2 vCPU / 4 GiB) from image `20261023-173758`:

- **Kernel panic** (`echo c > /proc/sysrq-trigger`): the VM was running again
  6 s later. Its shell and Claude Code sessions came back under the same IDs,
  Claude Code ran as `claude --continue`, and the "was restarted" alert arrived.
- **Deliberate stop:** the VM stayed stopped, and starting it again reopened
  nothing.
- **A save that can't be restored** (its checkpoint marked as from Firecracker
  1.16.0): resume failed twice, then the VM booted from the saved disk. A file
  written before the pause was there, the Codex session came back as
  `codex resume --last`, and the high-priority alert said why.
- **Disk growth:** 32 → 40 GiB while running (`df` in the guest showed 40G at
  once, data intact), and 40 → 44 GiB while stopped.
- **Logs:** `bun run logs host` and `bun run logs <vm>` showed hostd's log, the
  VM's console and its journal.
- **Old images:** the next build removed 8 old images, keeping the newest two
  and the one an existing VM was cloned from. The pool went from 29% to 12% full.
- The maximum run time, pool alerts and unanswered-guest alerts were checked by
  unit tests, not live; a 1-hour minimum and a nearly empty pool make them slow
  to provoke. Typechecking, 81 tests (one Linux-only skip) and the web build pass.

Not tested: a real host crash, so as not to disrupt others using the host. It
takes the same path as the kernel panic, starting from hostd's first pass after
boot.
