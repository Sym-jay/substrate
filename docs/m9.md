# M9: Windows workspaces

A Windows workspace is an EC2 instance of its own: Windows Server 2025 on an
`m8i.4xlarge` (16 vCPU, 64 GiB). In the browser you get its desktop and
PowerShell terminals. It comes with:
- Git
- Node LTS
- PowerShell 7
- Claude Code and Codex
- WSL, ready for `wsl --install -d Ubuntu`

It stops by itself when idle, and a stopped one costs only its disk.

## What it costs

| | |
|---|---|
| On | $1.63 an hour (`m8i.4xlarge` with the Windows licence, Mumbai) |
| Stopped | Its 100 GiB disk, about $9 a month |
| At once | 1 on at a time, so the account's 64 vCPUs cover it, the host (32) and the control box (2). The rest leaves room for an image build |

| Setting (control box) | Default |
|---|---|
| `SUBSTRATE_MAX_WINDOWS_RUNNING` | 1 |
| `SUBSTRATE_MAX_WINDOWS_PER_USER` | 2 |
| `SUBSTRATE_WINDOWS_IDLE_STOP_MINUTES` (each workspace can change its own in the UI) | 30 |
| `SUBSTRATE_WINDOWS_INSTANCE_TYPE` | `m8i.4xlarge` |

## How it works

```
browser ──WSS──▶ CloudFront ──▶ control box ──SSH (22)──▶ Windows: PowerShell 7
                                     │
                                     └──VNC (5900)──▶ Windows: TightVNC
```

- **No agent on Windows, no open ports.** The control box is in the same subnet,
  and the Windows security group lets in only the control box, on 22 and 5900.
  - **Terminals:** the control box runs `ssh` on a PTY (as for the Mac work)
    and relays it like any other terminal. PowerShell 7 is the SSH shell.
  - **Desktop:** the control box relays the browser's WebSocket to TightVNC
    byte for byte, as websockify does. noVNC draws it, scaled to fit, with
    touch.
- **Creating one** starts an instance from the newest Substrate Windows image
  (`/substrate/windows-ami`), through the `substrate-windows` launch template:
  security group, role, 100 GiB disk, and nested virtualization for WSL2. Its
  first boot (user data, `apps/control/src/windows/user-data.ts`):
  - sets Administrator's password to one of its own
  - signs in by itself from then on, so the desktop opens straight away
  - trusts the control box's SSH key, and turns password sign-in to SSH off
  - installs TightVNC with a VNC password of its own

  It's ready when the control box can SSH in and finds the first boot done:
  5 to 10 minutes.
- **Idle stop.** Every 30 seconds the control box checks each workspace's
  instance. It stops one that has gone its idle time without anyone using it,
  provided its CPU is quiet:
  - **Counts as use:** typing in a terminal, terminal output, and keyboard or
    mouse on the desktop.
  - **Quiet CPU:** no 5-minute average above 5% in the last 15 minutes. That
    covers an agent working with nobody watching.

  Stopping keeps the disk; **Start** brings it back in a couple of minutes.

The **Windows sign-in** button shows Administrator's password, for the sign-in
screen and for UAC prompts. It's kept in the control box's database, and the
first-boot user data has it too.

## The image

`bun run build:windows-image` (30 to 45 minutes, about $0.60):

1. Starts an `m8i.2xlarge` builder from AWS's latest Windows Server 2025 image,
   through the same launch template.
2. Runs `images/windows/provision.ps1` on it through SSM.
3. Restarts it (for WSL).
4. Generalizes it with EC2Launch's sysprep (`images/windows/sysprep.ps1`),
   which shuts it down.
5. Saves it as `substrate-windows-<date>` and points `/substrate/windows-ami` at it.

The builder is then terminated. Only the newest two images are kept.
Existing workspaces keep the image they started from.

When a step fails, `--keep` leaves the builder up, and `--builder <id>` carries
on with it without booting a new one. Terminate it yourself when you're done.

## Setting it up

1. `bun run deploy:infra`: the security group, role, launch template, the
   control box's permissions, and `/substrate/windows-subnet`.
2. `bun run build:windows-image`.
3. `bun run deploy:control`: the control box finds the subnet. The
   **Windows workspaces** panel appears once it's done.

## When something's wrong

- **A first boot that fails** (not ready within 30 minutes) leaves the workspace
  failed and its instance stopped.
- **On the instance, through Session Manager:**
  `aws ssm start-session --target <instance>`, then
  `Get-Content C:\substrate\first-boot.log`.
- **On the control box:** it logs each create, ready, idle stop and delete as
  `windows: …` (`bun run logs control`).

## Choices, and what's not done

- **VNC rather than Amazon DCV**, which the plan named. VNC fits the control
  box's WebSocket relay as it is. DCV would mean reverse-proxying its own HTTPS
  web app, but it streams video and would feel smoother on a phone. Worth
  switching to if VNC is too slow.
- **Terminals end** when the workspace stops or the control box restarts (a
  deploy). The desktop's windows, and the disk, are unaffected by a deploy.
- **No alerts** when a workspace stops itself (Linux VMs send them).
