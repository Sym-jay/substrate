# M8: Elastic memory

M8 starts a default 16 GiB workspace with a 4 GiB allocation, grows it under
memory pressure, and returns spare memory after sustained low use. `memMib`
continues to mean the workspace's configured ceiling. The web list shows live
allocation / limit, and `bun run vm memory VM` reports detailed measurements.

This branch starts from the latest M6/M7 `main` and also includes the review
follow-ups in PR #9, preserving their snapshot cleanup and release behavior.

## Policy and safety

Each cold boot installs Firecracker's standard virtio balloon with statistics
every second, free-page reporting, and emergency deflation on guest OOM. The
current guest kernel already has `VIRTIO_BALLOON`, `MEMORY_BALLOON` and
`PAGE_REPORTING`; M8 needs no new guest image or CloudFormation resources.

hostd polls every two seconds. It estimates the working set using actual balloon
size and the guest's available-memory report. It retains one GiB plus 20%
headroom, grows in jumps of at least two GiB, and waits 30 seconds of spare
capacity before reclaiming at most one GiB per pass. Missing or invalid stats
cannot trigger reclamation. An in-flight inflation is allowed to settle before
requesting another. Emergency deflation is acknowledged by subsequent policy
decisions, preventing the controller from immediately taking those pages back.

The lifecycle mutex serializes adjustments with boot, pause, fork and resize.
The balloon's state survives snapshots; resume/fork do not force a busy saved VM
back down to 4 GiB. hostd rebuilds its telemetry from the device after restarting.
Old running VMs and saves retain their original hardware until their next cold
boot adds the balloon. Small VMs keep their 4 GiB ceiling; medium VMs can grow to
8 GiB and standard VMs to 16 GiB.

**Capacity admission remains conservative.** Each running VM's maximum is still
reserved, including the host's existing reserve. Therefore all VMs can reach
their ceilings even when emergency deflation occurs. M8 reduces physical RAM
use; it does not yet increase the number admitted by overbooking their limits.
Dynamic admission above that reservation requires a separate host-wide pressure
and scheduling policy. This follows Firecracker's guidance that guest balloon
statistics are hints rather than host memory guarantees.

References: [Firecracker ballooning](https://github.com/firecracker-microvm/firecracker/blob/v1.17.0/docs/ballooning.md),
[pinned guest kernel config](https://github.com/firecracker-microvm/firecracker/blob/v1.17.0/resources/guest_configs/microvm-kernel-ci-x86_64-6.18.config).

## Measurements

`Vm.memory` is null for a stopped/paused VM or a running VM without a balloon.
Before the first sample, the limits are known and the measurements are null.

| Field | Meaning |
|---|---|
| `floorMib`, `limitMib` | Minimum allocation and configured ceiling |
| `targetMib` | Requested guest allocation: ceiling minus requested balloon |
| `actualMib` | Current guest allocation: ceiling minus actual balloon |
| `availableMib` | Guest estimate of reclaimable/available memory |
| `residentMib` | VMM process RSS measured on the host |
| `proportionalMib` | VMM process PSS measured on the host |
| `sampledAt` | Time of the last successful sample |

Allocated RAM is a budget, not the number of resident physical pages. Free-page
reporting can reduce RSS further. The capacity API's existing `memUsedMib` still
means reserved VM ceilings, not RSS.

## Deployment and acceptance

From this branch, with Bun 1.4.4 and the existing AWS credentials:

```sh
bun run typecheck
bun test
bun run deploy:host
bun run deploy:control
bun run check:m8
```

`check:m8` creates three default VMs with small disks and disables auto-pause
only on those VMs. It checks 4 GiB initial allocations and combined host RSS
below 16 GiB, then gradually writes 12 GiB in one guest. It verifies growth to
the 16 GiB ceiling, process/data survival through pause/resume, return to the
4 GiB floor after release, and RSS below 16 GiB again. It also checks hostd
restart recovery when no other workspace is active, and deletes its test VMs.
It never stops the EC2 host. Allow several minutes and at least 48 GiB of
unreserved host memory for the run.

Type checks and the production web build pass. The suite passes 108 tests with
one Linux-specific PTY test skipped on macOS. Desktop/mobile memory readouts
were checked without overflow.

AWS acceptance passed with the existing guest image:

| Check | Result |
|---|---|
| Three default VMs boot | 2,960 / 2,507 / 2,550 ms |
| Initial allocation | 4 GiB each, 16 GiB ceilings |
| Initial combined VMM RSS | 2,782 MiB (2.7 GiB), below 16 GiB |
| Memory pressure | Allocation grew to the 16 GiB ceiling; 12 GiB workload survived |
| Pause/resume under load | Same PID/data and continued progress; 245 ms resume |
| Released memory | Returned to the 4 GiB floor in 56 s |
| Combined RSS after reclaim | 2,177 MiB (2.1 GiB), below 16 GiB |
| hostd restart | VMs stayed running; controller rediscovered their targets |

`check:m6` also passed against M8: online disk growth, running-state forks,
independent parent deletion, checkpoints, rollback, resize, public previews,
binary WebSockets, SSH over CloudFront, and access denial/revocation. Its public
preview wake-up measured 302 ms. All acceptance-test VMs and probe artifacts
were cleaned up; the existing stopped workspace was left unchanged.
