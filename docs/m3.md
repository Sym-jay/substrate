# M3: pause and resume

Pause saves a running VM's memory, device state, and matching disk checkpoint.
The Firecracker process then exits, returning its RAM to the host. Resume restores
the same guest processes and terminal sessions; it does not boot a new guest.

## Use it

```sh
bun run vm pause demo
bun run vm resume demo
```

The workspace UI has **Pause** while running and **Resume** while paused.
Opening the same terminal after resume replays its scrollback. Typing to wake a
paused workspace is M4; in M3, click Resume first.

`vm start` on a paused VM also restores it, rather than discarding its saved
processes. `vm stop` refuses a paused VM: resume it before requesting a clean
shutdown. Deleting a VM removes its disk and checkpoints.

| Host API | Behaviour |
|---|---|
| `POST /vms/:id/pause` | Save and pause a running VM; already paused is idempotent |
| `POST /vms/:id/resume` | Restore a paused VM; already running is idempotent |
| `GET /vms/:id` | Includes `paused`, `pausing`, or `resuming` states and timing fields |
| Session / exec endpoints | Return 409 while paused or transitioning |

The control API proxies the same paths under `/api`. `pausedAt`, `pauseMs`, and
`resumeMs` are optional in the shared schema so the client can read older hostd
responses. `resumeMs` measures the resume request through guest-agent readiness,
including capacity checks and restoring the network. `bootMs` remains the last
cold boot time.

## Storage and ordering

Each checkpoint gets a new UUID. Its files live on the VM's ZFS filesystem:

```text
/var/lib/substrate/vms/<vm>/
  vm.json
  snapshots/<checkpoint>/state
  snapshots/<checkpoint>/memory

substrate/vms/<vm>/root@pause-<checkpoint>   # matching disk checkpoint
```

Pause freezes the vCPUs, asks Firecracker for a full snapshot with file syncing
enabled, and snapshots the root zvol after Firecracker has drained and synced
its block device. It syncs the pool and atomically publishes `vm.json`, including
an fsync of the file and directory. Only then does it kill the frozen VMM and
remove the TAP device. A graceful guest shutdown at this point would invalidate
the pairing of memory and disk, so pause deliberately skips it.

Resume rolls the disk back to that checkpoint, recreates the TAP, starts a fresh
unconfigured Firecracker process, and loads the saved state with the File memory
backend. It repopulates MMDS before resuming the vCPUs, then waits for guestd to
answer. The checkpoint records the Firecracker version and rejects a different
installed version. The guest clock accounts for time spent paused.

The memory file stays unchanged while a restored VMM uses it. A subsequent pause
writes a separate generation and cleans up the previous one only after its VMM
has exited. The checkpoint directory is private to root.

## Recovery

- A failed snapshot before manifest commit thaws the original VM and removes
  its incomplete checkpoint. If clearing the manifest fails, the VM stays frozen
  until startup reconciliation can safely resolve it.
- A committed pause survives hostd or host restarts. If hostd died before killing
  the frozen VMM, startup finishes that step.
- An interrupted pause without a committed checkpoint resumes the still-live VMM
  in place when hostd starts again.
- A failed restore keeps the paused checkpoint. Retry rolls back the matching
  disk again, including any writes made during the failed attempt. It never
  silently falls back to a cold boot.

Lifecycle operations are serialized, including boot readiness, so delete or pause
cannot race a boot that later writes stale metadata. Paused VMs do not reserve
RAM once their Firecracker process is gone. Snapshots share the host's data disk;
full snapshots can take tens of seconds to save. Incremental (diff) snapshots
were planned for M7 and dropped. Recovery of a crashed *running* VM, and a fresh
boot when a save can't be restored, came in M7 (`docs/m7.md`).

## Verify on AWS

```sh
bun run typecheck
bun test
bun run check:m3
bun run check:m3 --host-cycle
# Also enforce the original latency target:
bun run check:m3 --host-cycle --strict-latency
```

The checker creates and deletes its own default VM. It verifies M2's reconnect
behaviour, then performs repeated pause/resume cycles. Every verification asks
the shell for fresh output containing a new nonce, its original memory-only
variable, its PID, and a disk marker. It also checks scrollback, RAM accounting,
409 responses while paused, and resume timings against the 500 ms target.
By default, timing misses are reported separately from functional failures;
`--strict-latency` makes a miss fail the run.

Without `--host-cycle`, it tests a hostd restart and explicitly leaves the host
stop/start requirement unverified. With `--host-cycle`, it stops and starts EC2
while the VM is paused. It refuses the operation if another VM exists and returns
a host stopped by the checker to its original running state, including on failure.

### AWS results, 2026-10-23

- Default VM: 6 vCPU / 16 GiB; booted in 2,355 ms.
- Repeated resumes: 240 ms and 239 ms.
- After a full EC2 stop/start: 604 ms. The saved memory-only shell variable,
  original shell PID, disk marker, and terminal scrollback all survived, with
  fresh terminal output verified after restore.
- The 604 ms cold resume is accepted for this milestone; reducing it below the
  original 500 ms target is deferred. Warm resumes meet the target.

For the later multi-size profiling, cold-host measurements, optimizations and
remaining latency targets, see [VM performance](performance.md).
- Full pauses took approximately 7–42 seconds, and each released the VM's
  16 GiB memory allocation. Paused terminal requests returned 409.
- The checker deleted its test VM. Typechecking, 50 local tests, and the web
  production build passed. One existing Linux-only terminal test is skipped on
  macOS. The Pause/Resume UI was also checked at desktop and mobile widths.

The API client types are generated from Firecracker v1.17.0's Swagger definition:

```sh
bun run generate:firecracker
```

The generated file records the source URL and SHA-256. See Firecracker's
[snapshot documentation](https://github.com/firecracker-microvm/firecracker/blob/v1.17.0/docs/snapshotting/snapshot-support.md)
for its snapshot and memory-file lifetime contract.
